# Red Team Plan Review — Security Adversary / Fact Checker

Scope: `plans/260810-2258-colimaui-p0-polish-parity/*` and `plans/260810-2258-colimaui-commercial-foundation/*`.
Method: hostile read of plan text + grep/glob verification against the actual Rust/Svelte source. Advisory only; no plan file was modified.

Pre-existing conditions that every finding below inherits (verified):
- `src-tauri/src/api_server.rs:231` — `GET /api/auth/token` is on the **unauthenticated** router. Any local process gets the bearer token for free.
- `src-tauri/src/api_server.rs:204` + `src-tauri/src/routes/kb.rs:13-15` — `GET /api/settings` returns **all** settings via `knowledge_bank::get_all_settings()`, and `src/lib/settingsStore.svelte.ts:13` confirms `ai_api_key` is one of those keys.
- `src-tauri/src/commands/ai_chat.rs:174` and `:477` — the Gemini provider puts the user's API key in the **URL query string**.
- `src-tauri/src/validation.rs` has validators only for container IDs, k8s names and AppleScript. There is **no** instance/profile validator, and `grep -rn "validation::"` matches only 3 files (`api_server.rs`, `commands/lima.rs`, `commands/containers.rs`).

## Finding 1: Error-detail panel + "Ask AI about this error" turns an existing secret leak into a product feature
- **Severity:** Critical
- **Plan:** Plan 1 (p0-polish-parity)
- **Location:** Phase 1, sections "Requirements → Functional" and "Architecture" (`ColimaError { ..., command, exit_code, stderr, hint }`)
- **Flaw:** The phase mandates surfacing `command`, `exit_code` and `stderr` in a copyable UI panel, plus a one-click "Hỏi AI về lỗi này" that pushes the *whole* error context into `AiChatPanel` (i.e. to a third-party LLM endpoint). The only stated mitigation is cosmetic: `$HOME → ~`. There is no redaction of query strings, argv, env vars or tokens.
- **Failure scenario:** User configures Gemini. `list_gemini_models` builds `https://generativelanguage.googleapis.com/v1beta/models?key=<SECRET>` (`ai_chat.rs:174`). The request fails offline; the handler returns `format!("Request failed: {}", e)` (`ai_chat.rs:180`), a `reqwest` error whose Display chain includes the URL. Under Phase 1 this string becomes `AppError.stderr`, is rendered in `ErrorLogPanel`, retained in the session error-log store, offered as "copy toàn bộ context", and — one click later — is transmitted verbatim to the user's LLM provider (and to crash reporting once Plan 2 Phase 4 lands). The user's paid API key is exfiltrated by the feature designed to help them.
- **Evidence:** `src-tauri/src/commands/ai_chat.rs:174,180,477`; plan text: "Toast lỗi phải mở được panel 'Chi tiết lỗi' chứa: lệnh đã chạy, exit code, stderr, thời điểm" and "Nút 'Hỏi AI về lỗi này' đẩy nguyên context lỗi vào `AiChatPanel`"; sole mitigation row: "stderr chứa đường dẫn nhạy cảm | Rút gọn `$HOME` thành `~`".
- **Suggested fix:** Add an explicit `redact()` stage in `helpers::error_from_output` and in `normalizeError()`: strip all URL query strings, drop anything matching `key=|token=|Bearer\s+\S+|x-api-key`, never include the full argv (store a command *label*, not the rendered command line), and never include process env. Make "Ask AI" show the exact redacted payload for review before send. Add a Rust unit test that feeds a Gemini-style URL through the error path and asserts the key is gone — that test is the acceptance criterion, not the `$HOME` rewrite.

## Finding 2: Phase 6's DNS + reverse proxy gives any website a route into the user's containers and into the loopback API
- **Severity:** Critical
- **Plan:** Plan 1 (p0-polish-parity)
- **Location:** Phase 6, "Architecture" (`resolver.rs`, `proxy.rs`) and "Implementation Steps" 3-4
- **Flaw:** The design is: a local DNS server answers `127.0.0.1` for every name under a wildcard suffix, and a reverse proxy on 80/443 selects the upstream **purely from the `Host` header**. There is no requirement anywhere in the phase for Host allowlisting against the registry, Origin checking, or protection of the co-resident loopback HTTP API. This is a textbook DNS-rebinding / browser-driven SSRF enabler, and it is being added to a machine that already exposes an unauthenticated token endpoint on loopback.
- **Failure scenario:** (a) The user visits `evil.example`. The page issues `fetch('http://api.myproject.colima.local/admin/delete', {mode:'no-cors'})`. Because the local resolver maps the whole wildcard to loopback and the proxy routes by `Host`, the request lands inside the user's container network — no CORS needed for state-changing GET/POST side effects. Every container the developer runs is now reachable from any page they open. (b) Worse: `evil.example` rebinds its own A record to `127.0.0.1`; the page is then *same-origin* with `http://evil.example:11420`, so the `CorsLayer` origin allowlist at `api_server.rs:55-63` is irrelevant, the page fetches `/api/auth/token` (unauthenticated, `api_server.rs:231`), then `GET /api/settings` and reads `ai_api_key`, then drives every container/instance endpoint. Phase 6 does not create the rebinding primitive by itself, but it ships a resolver and a proxy that normalise loopback-name traffic and it never adds the Host-header defence that closes it.
- **Evidence:** `src-tauri/src/api_server.rs:231` (`/api/auth/token` on public router), `:204` + `src-tauri/src/routes/kb.rs:13` (`/api/settings` returns all settings), `:55-63` (origin allowlist only), `src/lib/settingsStore.svelte.ts:13` (`ai_api_key` is a stored setting); plan text: "`proxy.rs` — reverse proxy HTTP/HTTPS/WS (hyper/axum), chọn upstream theo SNI/Host" and "resolver.rs: DNS server trên port cao, trả `127.0.0.1` cho suffix đã đăng ký" — no Host/Origin validation requirement, no mention of the loopback API's exposure.
- **Suggested fix:** Make these blocking requirements of Phase 6 step 4: (1) proxy rejects any request whose `Host` is not an **exact** entry in the registry (no suffix matching); (2) proxy rejects requests carrying an `Origin`/`Sec-Fetch-Site: cross-site` that is not itself a registered domain; (3) the resolver answers only exact registered names, NXDOMAIN for everything else including unknown labels under the suffix; (4) as a prerequisite, add a Host-header allowlist middleware to `api_server.rs` (accept only `127.0.0.1:*`/`localhost:*`) and move `/api/auth/token` behind an origin/process check — otherwise the rebinding path stays open with or without Phase 6.

## Finding 3: Unvalidated profile name flows into argv today and into filesystem writes under Phase 5; Phase 3 cites a validator that does not exist
- **Severity:** Critical
- **Plan:** Plan 1 (p0-polish-parity)
- **Location:** Phase 3, "Implementation Steps" step 4 + Risk row "Menu item id bị lợi dụng để inject lệnh"; Phase 5, "Architecture" (`write_instance_config`) and step 4
- **Flaw:** Phase 3 asserts "Validate tên instance qua `crate::validation` trước khi truyền vào lệnh … giống mọi command khác" — factually wrong on both halves. `validation.rs` contains no instance/profile validator, and profile names are currently passed to `colima` with **zero** validation. Phase 5 then takes that same unvalidated name and uses it to build a filesystem path that it writes to and backs up. The plan's risk table treats this as already-handled.
- **Failure scenario:** Phase 5 exposes `write_instance_config(name, cfg)` over both Tauri IPC and an HTTP route (the plan explicitly requires dual-mode). A local process fetches the bearer token from `/api/auth/token` (unauthenticated) and POSTs `name = "../../../../Users/victim/Library/LaunchAgents/evil"`. `read_instance` builds paths as `colima_home.join(profile).join("colima.yaml")` (`instance_reader.rs:76`) with no canonicalisation and no prefix assertion, so the "atomic write + .bak" logic happily writes attacker-controlled YAML outside `~/.colima`. Even without traversal, `.bak` creation with no `O_NOFOLLOW` is a symlink-clobber primitive: pre-plant `~/.colima/default/colima.yaml.bak` as a symlink to a file the user can write, and the backup step overwrites it. Separately, a profile named `--vm-type` or `-h` is injected as a bare argv element at `colima.rs:93-95` and friends, giving flag injection into the `colima` invocation.
- **Evidence:** `src-tauri/src/validation.rs:1-97` (no profile/instance validator; only `is_valid_container_id`, `is_valid_k8s_name`, `contains_shell_injection`, `escape_applescript`); `grep -rn "validation::" src-tauri/src` matches only `api_server.rs`, `commands/lima.rs`, `commands/containers.rs`; `src-tauri/src/commands/colima.rs:93-95,176-178,208-210,260-262,312-314,351-355,393-395` all push `profile` straight into argv unvalidated; `src-tauri/src/instance_reader.rs:76` `colima_home.join(profile).join("colima.yaml")`; plan text Phase 3 step 4 and Phase 5 step 4 ("backup `.bak` có timestamp, ghi atomic").
- **Suggested fix:** Add `validation::is_valid_profile_name` (`^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$`, explicitly rejecting leading `-` and any `.`/`/`) as a **Phase 3 deliverable**, apply it at the HTTP route boundary and at every `colima.rs` entry point, and make Phase 5 additionally canonicalise the resolved path and assert it is a prefix of `colima_home()` before any write. Backups must be created in the same directory with `O_NOFOLLOW`/`O_EXCL` semantics, not by blind path write. Phase 3's risk-table claim "giống mọi command khác" should be deleted — it is not true of the current code.

## Finding 4: Local CA install has no name constraints and no automated uninstall verification
- **Severity:** High
- **Plan:** Plan 1 (p0-polish-parity)
- **Location:** Phase 6, "Architecture" (`ca.rs`, `install.rs`), "Tests / Validation" (final two bullets), Risk row "Cài CA vào trust store hệ thống…"
- **Flaw:** The plan installs a self-generated CA into the **system** trust store and stores the private key at `~/.colima-ui/ca/` with mode 0600. It specifies no X.509 `nameConstraints`, no restriction of the trust setting to the domain suffix, and no key protection beyond POSIX mode. Uninstall correctness is validated by manual steps only ("Thủ công: gỡ cài đặt → CA biến mất khỏi Keychain"). 0600 is meaningless against the actual threat here, because everything else on this box already assumes the same-user boundary is worthless (the token endpoint hands out API credentials to any same-user process).
- **Failure scenario:** Any malicious npm postinstall script / random `curl | sh` the developer runs — i.e. the same user — reads `~/.colima-ui/ca/ca.key`. Because the CA is unconstrained and system-trusted, the attacker can now mint a valid-looking certificate for `login.bank.com` and MITM the developer's browser and CLI tooling for the lifetime of the CA. The developer never sees a warning, because they clicked "trust" once for a container-domains feature. If the uninstall path has a bug (only tested manually), the CA survives feature removal and app uninstall.
- **Evidence:** plan text Phase 6 step 5 ("sinh CA (lưu `~/.colima-ui/ca/`, quyền 0600)") and step 7; test list contains only "Bảo mật: CA private key không nằm trong log, không nằm trong bundle, quyền file 0600" — nothing about CA scope; contrast with the already-demonstrated same-user exposure at `src-tauri/src/api_server.rs:231` + `src-tauri/src/routes/kb.rs:13-15`, which shows this codebase currently grants any same-user process the API token and the stored `ai_api_key` (`src/lib/settingsStore.svelte.ts:13`).
- **Suggested fix:** Make these Phase 6 acceptance criteria: (1) CA certificate carries `nameConstraints` permitting only the chosen suffix (and excluding everything else) — this is the single control that caps blast radius; (2) on macOS install with a constrained trust policy (`security add-trusted-cert` with SSL-only policy) rather than blanket trust; (3) store the CA key in Keychain/`secret-service` where available, file fallback only; (4) add an **automated** uninstall test asserting the cert is absent from the trust store and `/etc/resolver/<suffix>` is gone; (5) short CA lifetime with documented rotation.

## Finding 5: Sidecar discovery via environment variable is arbitrary code execution inside the trusted app, and "0600 socket" is not peer authentication
- **Severity:** High
- **Plan:** Plan 2 (commercial-foundation)
- **Location:** Phase 1, "Implementation Steps" step 3 and "Requirements → Non-functional"
- **Flaw:** `bridge.rs` is specified to locate the sidecar via "đường dẫn cạnh executable + biến môi trường dev" and spawn it at startup. The plan's only security requirements are a 0600 socket and "same user, no root". A 0600 socket restricts *other users*; it provides no authentication of the peer, and an env-var-selected binary is not a trust boundary at all. The plan explicitly parks sidecar spoofing as "Thấp — chấp nhận", which is defensible for entitlement fraud but is the wrong analysis: the damage is not a free Pro licence, it is code execution in a process that controls Docker.
- **Failure scenario:** This codebase already honours environment overrides (`instance_reader.rs:52` reads `COLIMA_HOME`) and already resolves binaries through `which`/PATH (`path_util.rs:142-163`), so a dev-mode env override will ship in release builds by pattern. Attacker (or a compromised dev dependency) sets `COLIMA_UI_PRO_PATH=/tmp/evil` in the user's launch environment or drops a binary next to the executable on Linux. On next launch the signed, user-trusted ColimaUI spawns the attacker binary as a child process — inheriting the user's session, the Docker socket, and (via `/api/auth/token`) the full local API. The attacker also answers `license.status` and every `invoke`, so all Pro "capabilities" are attacker-controlled code paths rendered in the UI.
- **Evidence:** `src-tauri/src/path_util.rs:142-163` (`resolve_binary` trusts `which`/PATH), `src-tauri/src/instance_reader.rs:52` (`COLIMA_HOME` env override precedent), `src-tauri/src/api_server.rs:231` (child process can read the API token); plan text: "tìm sidecar (đường dẫn cạnh executable + biến môi trường dev), spawn, handshake" and risk row "Sidecar bị giả mạo để mở Pro | Thấp — chấp nhận | Không đầu tư chống".
- **Suggested fix:** Gate the env-var path behind `#[cfg(debug_assertions)]` so it cannot exist in release builds. In release, resolve the sidecar only from a fixed path inside the app bundle and verify its code signature / notarisation before `spawn` on macOS. Place the socket in a 0700 directory under `$HOME` (never `/tmp`), and authenticate the peer on `accept` with `SO_PEERCRED`/`LOCAL_PEERCRED` (uid match) plus a nonce handed to the child at spawn time. Re-rate the "sidecar spoofing" risk from "Low — accepted" to "code execution" and state the accepted residual explicitly.

## Finding 6: Deep-link activation treats the licence key as trusted input and can carry an attacker-chosen server endpoint
- **Severity:** High
- **Plan:** Plan 2 (commercial-foundation)
- **Location:** Phase 3, "Architecture" (`colima-ui://activate?key=…`) and "Implementation Steps" step 9
- **Flaw:** The mitigation is "always confirm + validate signature before applying". Confirmation dialogs are not a control against a payload that is parsed *before* the user answers, and the plan never states that the licence-server URL is compile-time constant. Phase 2's key payload is described as "JSON gọn + chữ ký, encode base64" — if the payload (or a future field) carries an endpoint or a display string, the deep link becomes a remote-controlled network + UI injection primitive.
- **Failure scenario:** A web page navigates to `colima-ui://activate?key=<10MB base64>`; the handler base64-decodes and `serde_json`-parses before any signature check, giving a trivial memory/CPU DoS on a scheme any page can trigger without user interaction. A subtler variant: the crafted payload contains a plausible `email`/`tier` and an `endpoint` field; the confirmation dialog renders attacker-controlled text ("Activate Pro for you@company.com"), the user clicks yes, and `activation.rs` POSTs the machine fingerprint to the attacker's server — a fingerprint the plan promises is never disclosed. The app's HTTP capability already permits `https://*`, so nothing at the Tauri layer blocks the outbound call.
- **Evidence:** `src-tauri/capabilities/default.json` — `"http:default"` allows `{ "url": "https://*" }` plus `http://localhost:*` and `http://127.0.0.1:*`; `src-tauri/tauri.conf.json:31` CSP `connect-src` similarly permits `http://127.0.0.1:*` and named provider hosts; plan text Phase 3 step 9 ("validate key trước khi áp dụng, luôn hỏi xác nhận") and Phase 2 requirement "Không gửi bất kỳ dữ liệu nào ngoài license id + machine fingerprint".
- **Suggested fix:** Hard-code the licence server origin in the sidecar; make it a documented invariant that no field of a licence key can influence any URL. Cap the deep-link parameter length (e.g. 4 KB) and charset before decoding. Deep link must only *populate the input field* in the License settings page — never initiate a network call — so signature verification always happens on an explicit user action. Add a negative test for oversized/garbage deep links to the Phase 3 test list (currently only "không gây crash").

## Finding 7: The "closed enum prevents PII" guarantee does not cover crash reports, which is where the PII actually is
- **Severity:** High
- **Plan:** Plan 2 (commercial-foundation)
- **Location:** Phase 4, "Architecture" (decision note on `events.rs`) and "Requirements → Functional — Crash reporting"
- **Flaw:** The plan's headline control — "`events.rs` dùng enum đóng, không nhận chuỗi tự do. Đây là biện pháp kỹ thuật ngăn rò rỉ PII, mạnh hơn mọi cam kết bằng lời" — applies only to telemetry events. Two lines later the same phase ships crash reporting that sends "stack + version + OS", which is by definition free-form text. The success criteria ("Sự kiện không thể chứa chuỗi tự do (enforce ở kiểu dữ liệu)") never mention the crash channel, and `docs/telemetry.md` is scoped to `events.rs`.
- **Failure scenario:** A panic occurs in an error path that has already formatted user data into a message — the codebase does this routinely: `colima.rs:197,229` format instance names into result strings, `ai_chat.rs:180` formats a reqwest error carrying the Gemini URL **with the API key in the query string** (`ai_chat.rs:174,477`), `shell_sandbox.rs` returns raw command stdout up to `MAX_OUTPUT_BYTES`. The panic payload and the surrounding frames go to the crash endpoint under a consent screen that told the user "no user data". The published `docs/telemetry.md` is then simply false, which is the exact reputational failure the phase is trying to avoid.
- **Evidence:** `src-tauri/src/commands/ai_chat.rs:174,180,477`; `src-tauri/src/commands/colima.rs:197,229`; `src-tauri/src/commands/shell_sandbox.rs:29` (`MAX_OUTPUT_BYTES` — raw output is returned to callers); plan text Phase 4: "Bắt panic Rust + lỗi JS chưa xử lý; đính kèm stack + version + OS, **không** đính kèm dữ liệu người dùng" vs. success criterion listing only event-level enforcement.
- **Suggested fix:** Route crash reports through the same redactor as Finding 1, and make that a shared, tested module (not two implementations). Drop the panic *payload string* entirely — send only file:line and a hash of the message. Strip absolute paths and all URL query strings from frames. Add a unit test that panics with a message containing a fake API key and asserts it is absent from the serialised report, and extend the success criteria + `docs/telemetry.md` to cover the crash channel explicitly. Show a real sample crash report in the consent dialog, not a description of one.

## Finding 8: Compose files go to a third-party LLM with only a warning dialog protecting the secrets they contain
- **Severity:** High
- **Plan:** Plan 2 (commercial-foundation)
- **Location:** Phase 5, "Kiến trúc lai" tier 3 + "Requirements → Non-functional", Risk row "Gửi file compose chứa secret lên LLM"
- **Flaw:** Tier 3 sends "file compose + lỗi + kết quả tầng 1-2" to the user's LLM provider. The mitigation is a pre-send warning and optional masking ("cho phép che biến môi trường") — opt-**in** redaction on a data class that is secret by default. Compose files routinely carry `environment:` values, `POSTGRES_PASSWORD`, registry credentials, and `env_file:` references. Note the phase also lists tier-3 input as including the Phase 1 error context, which per Finding 1 may itself contain the user's provider key — sent to the provider whose key it is, and potentially to a *different* provider than the one it belongs to.
- **Failure scenario:** Developer hits a compose error, clicks "Phân tích & sửa", skims the "we will send this" dialog (as users do), and their production `POSTGRES_PASSWORD` and `DOCKERHUB_TOKEN` are posted to an LLM provider and retained in that provider's logs/training pipeline. For Gemini the request URL itself carries their key (`ai_chat.rs:477`), so a proxy/log on the path sees both the secrets and the credential.
- **Evidence:** `src-tauri/src/commands/ai_chat.rs:477` (`{}/models/{}:generateContent?key={}`), `:531-532` (Authorization header path); `src-tauri/src/commands/compose.rs` (173 lines) has no redaction helper today; plan text Phase 5: "Tầng 3 phải nói rõ sắp gửi gì cho provider nào trước khi gửi" and risk mitigation "cho phép che biến môi trường".
- **Suggested fix:** Invert the default: redact by **schema**, not by blacklist — drop every value under `environment`, `secrets`, `x-*`, and never read/inline `env_file` contents; send keys and structure only, with per-field opt-in to unredact. Display the post-redaction payload byte-for-byte in the confirm dialog. Add a test asserting that a compose fixture containing a known secret string never appears in the tier-3 request body. (Phase 6 already applies this reasoning to config sync — "lọc bỏ mọi secret ở tầng schema chứ không bằng blacklist"; Phase 5 must match it.)

## Finding 10: Both plans build on an auth middleware with a substring token compare and a suffix-based bypass
- **Severity:** Medium
- **Plan:** Plan 1 (p0-polish-parity) and Plan 2 (commercial-foundation)
- **Location:** Plan 1 Phase 1 "Tests/Validation" (browser-mode parity at `:11420`); Plan 2 Phase 4 "Architecture" (`sink.rs`, crash reporting)
- **Flaw:** Neither plan touches `auth.rs`, yet both expand what flows across it. The middleware authenticates SSE by `query.contains(&format!("token={}", expected))` — a substring test on the raw query string — and it selects that branch for **any** path ending in `/stream`. Both plans add streaming/eventing surface (tray subscriptions, error events, telemetry, log panels), so the suffix rule will start matching routes nobody audited.
- **Failure scenario:** A future route added by Plan 1 Phase 3/6 or Plan 2 Phase 4 named `.../stream` silently opts out of header auth and into query-string auth. Meanwhile the token now travels in URLs, and Plan 1 Phase 1 (`command`/`stderr` capture, copyable error log) plus Plan 2 Phase 4 (crash stacks, telemetry sink) are exactly the systems that persist and transmit URLs — so the local API bearer token starts appearing in error logs and crash reports the user is invited to share. Comparison is also non-constant-time and matches anywhere in the query, so `?x=token=<guess>` style probing is not cleanly rejected.
- **Evidence:** `src-tauri/src/auth.rs:38-43` (`path == "/api/events" || path.ends_with("/stream")`, then `query.contains(...)`), `:47-52` (`auth_str == format!("Bearer {}", expected)`); only one such route exists today — `src-tauri/src/api_server.rs:182` `/api/k8s/pods/logs/stream`; plan text Plan 1 Phase 1: "Thủ công: browser mode (`:11420`) hiện lỗi giống hệt desktop mode"; Plan 2 Phase 4: `sink.rs — HTTP tới endpoint thu thập`.
- **Suggested fix:** Replace the suffix rule with an explicit route allowlist and parse the `token` query parameter properly (constant-time compare). Add `token` to the redaction list from Finding 1 so it can never reach the error log, the clipboard, an LLM prompt, or a crash report. Both plans should carry this as a shared prerequisite item rather than assuming the middleware is sound.

## Cross-cutting notes for the planner

1. **One redactor, three consumers.** Findings 1, 7, 8 and 10 all resolve to the same missing component: a single tested `redact()` used by the error path, the crash reporter, the telemetry sink, and the LLM tier. It belongs in Plan 1 Phase 1 as a first-class deliverable with its own test file, and Plan 2 Phase 4/5 should declare a dependency on it. Today the two plans each hand-wave their own partial mitigation.
2. **Same-user is not a boundary in this codebase.** Plan 2 Phase 1 (0600 socket), Phase 2 (`license.json` 0600) and Plan 1 Phase 6 (CA key 0600) all lean on POSIX mode as the security argument. `api_server.rs:231` already hands the API token to any same-user process, which then reads `ai_api_key` via `/api/settings`.
