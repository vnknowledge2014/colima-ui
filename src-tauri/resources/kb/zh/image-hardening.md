# 加固容器镜像

## 安全页面在检查什么

两个独立的问题。**已知漏洞**来自 Trivy：镜像里的软件包是否有已公开的安全公告。
**配置**来自 ColimaUI 对镜像本身应用的规则——它以什么身份运行、从哪里来、有多旧。
一个镜像可以补丁齐全却配置糟糕，这正是分数分成四部分而不是一个的原因。

## 最值得先做的改动

**不要以 root 运行。** 没有 `USER` 指令，进程就以 uid 0 启动。在镜像里创建账号，
并在 Dockerfile 结尾切换过去：

```dockerfile
RUN adduser --system --no-create-home app
USER app
```

如果服务需要 80 端口，就在容器内监听 8080，再用 `-p 80:8080` 映射出去。需要绑定
低端口，通常正是镜像至今仍以 root 运行的原因。

**把凭据移出镜像。** `ENV` 里的任何值都会随镜像的每一份副本一起分发，并在
`docker inspect` 中可见。请在运行时传入：

```bash
docker run --env-file ./secrets.env myapp:1.2.3
```

仅仅去掉值重新构建并不够——包含该值的层仍然留在推送过的任何registry里。请轮换
这个凭据。

**固定你部署的东西。** 标签是一个位置，不是一个镜像：`latest`、`stable`，甚至
`1.27`，都会在补丁发布时被重新推送。给发布打完整版本号，在重要的地方按摘要部署：

```bash
docker pull nginx@sha256:...
```

**按计划重建。** 基础镜像持续收到软件包更新。半年没有重建的镜像，不可能包含构建
之后发布的任何修复，无论今天的扫描结果多干净。

**记录来源。** 两个标签能把机器上一个来历不明的镜像变成可追溯的东西：

```dockerfile
LABEL org.opencontainers.image.source="https://github.com/you/app"
LABEL org.opencontainers.image.revision="$GIT_SHA"
```

## 把镜像变小，通常就是把它变安全

大多数发现来自应用从不调用的软件包。`-slim` 或 `-alpine` 基础镜像，或者只装载
编译产物的多阶段构建，会连同"必须为它们打补丁"的理由一起移除它们。安全页面会为
常见基础镜像给出替代建议。

要清楚替换会改变什么：Alpine 使用 musl 而非 glibc，原生依赖可能需要重新构建；
distroless 镜像根本没有 shell——这正是它更安全的原因，也正是在其中调试更难的原因。

## 关于分数

这个数字用于排序列表。四个分项才是答案：它们说明问题出在 CVE、配置、来源还是年龄，
而这些需要做的事情各不相同。

分数只能与使用**相同**扫描器、**相同**漏洞库日期、**相同**规则包版本算出的分数
比较，所以这三项就印在它旁边。不同扫描器在同一镜像上的差异可以超过十倍；这是漏洞
数据的性质，而不是某个工具的缺陷。

## 严格程度

L1 是几乎每个镜像都应做到的。L2 增加了对多数服务合适的建议。L3 很严格，其中一部分
不适用于具体某个镜像。提高级别只会让分数变低——它只会启用更多规则，不会更少。

## 规则从哪里来

ColimaUI 的规则由本项目撰写。它们引用已公开标准的条目编号（例如 CIS Docker
Benchmark §4.1）以便你查阅原始讨论，但措辞、评分与建议都是我们自己的。ColimaUI
未获 CIS 或 OWASP 认证，与其无关联，也未获其背书。
